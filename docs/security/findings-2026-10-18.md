## Findings (most severe first)

### [High] Pending pairings are unbounded, so pairing spam exhausts the Mac's memory
- Area: Pairing
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:394-413, 907-910, 945-948
- What: Every `POST /pair/request` with a new `deviceId` runs an ECDH and adds a `PendingPairing` to a dictionary that is only pruned after 110 s. There is no cap on entries and no per-source rate limit. Each entry keeps the caller's `deviceName` and `features`, which together can be close to the 64 KB body limit.
- Attack: Someone on the same Wi-Fi loops `/pair/request` with random UUIDs and ~64 KB names. At a few hundred requests a second that is gigabytes of memory inside the 110 s window. The Mac app slows down, then gets killed, so it stops receiving files. No dialog appears, so the user sees nothing.
- Fix: Cap pending pairings (for example 8 in total and 1 per source address), refuse more with `429`, and cap `deviceName` (for example 64 characters) and `features` (for example 16 short entries) when decoding.

### [High] Mac connections have no read timeout and no cap, so an unpaired LAN host can tie up the receiver
- Area: Transport and upload
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:124-130, 171-180 (accept with no limit), 313-352 (`receiveRequestHead`), 354-392 (`receiveSmallBodyIfNeeded`), 722-758 (upload `receiveMore`)
- What: No `NWConnection` read has a deadline, and neither listener limits how many connections are open. A connection that sends half a header, or a `Content-Length` it never finishes, stays open for good. Each one holds up to 64 KB of buffer and a file descriptor.
- Attack: Someone on the same Wi-Fi opens a few thousand connections to port 49152 and sends one byte now and then (slowloris). The Mac app runs out of file descriptors. New connections, pairings and file writes then fail until the app is restarted. No pairing is needed.
- Fix: Close a connection that hasn't sent a full header within ~10 s or a small body within ~10 s. Close an upload that makes no progress for ~30 s, except while it waits for the user's decision. Cap open plain-port connections (for example 32 in total, 4 per source address) and secure-port connections (for example 8).

### [High] Unconfirmed: a half-closed pairing request may spin the Mac's main thread
- Area: Transport and upload
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:371-389
- What: `receiveSmallBodyIfNeeded` never checks `isComplete`. If the client sends fewer body bytes than `Content-Length` and then half-closes, every later `receive` returns at once with no data and no error, and the function calls itself again. The upload path already guards against this exact case ("asking again would spin", line 741). Not run.
- Attack: Someone on the same Wi-Fi sends `POST /pair/request` with `Content-Length: 1000` and 10 bytes, then `shutdown(SHUT_WR)`. If the loop spins as expected, the main queue runs at 100% CPU and the UI and all request handling freeze. One connection is enough, and no pairing is needed.
- Fix: In the receive callback, if `isComplete && body.count < expectedLength`, cancel the connection (or return 400). Add a LinkBridgeCoreChecks case that half-closes mid-body.

### [High] The Android receiver has 4 worker threads and a per-read timeout, so 4 slow connections block all transfers
- Area: Transport and upload
- Where: android/app/src/main/java/com/linkbridge/android/ReceiveServer.kt:30, 43-47, 67-73, 279, 284
- What: Each accepted socket goes to a fixed pool of 4 threads, which then runs the TLS handshake. `soTimeout` is 15 s per `read`, not per handshake, so a client sending one byte every 14 s keeps a thread forever. Extra sockets wait in the executor's unbounded queue, each holding a file descriptor. A transfer waiting for the user's approval also holds a thread.
- Attack: Someone on the same Wi-Fi opens 4 connections to port 49153 and trickles a ClientHello. All workers are busy, so the user's real transfers hang and then time out on the sender. More connections pile up in the queue until the process runs out of file descriptors. No pairing is needed.
- Fix: Set an overall handshake deadline (for example, close the socket from a scheduled task if the handshake hasn't finished in 10 s) and a header deadline after it. Use a bounded queue and refuse (close) sockets when it is full. Wait for approval off the worker thread, or count those waits separately from the handshake pool.

### [High] macOS keeps the long-term pairing private key and every peer secret in a plaintext file
- Area: Secret storage
- Where: macos/Sources/LinkBridgeCore/CredentialStore.swift:49-119; macos/Sources/LinkBridgeCore/PairingKeyStore.swift:28-35; macos/Sources/LinkBridgeCore/TrustedPeerStore.swift:45-46, 67-68
- What: `credentials.json` (mode 0600, in the sandbox container's Application Support) holds, unencrypted, the Mac's P-256 pairing private key (`identity.pairingPrivateKey`) and each paired device's secret (`peer.<id>`). This is the known ad-hoc-signing trade-off in the skill, listed so it gets fixed before store release. It counts more because secrets never rotate (see "Re-pairing produces the same secret").
- Attack: A malicious app on the same Mac that can read the container, such as anything the user has given Full Disk Access, or anyone with a copy of an unencrypted Time Machine backup or Migration Assistant transfer. With the private key and the phones' public keys, they can recompute every pairing secret. They can then send files to the Mac as any paired phone, and to any paired Android phone as the Mac. The access lasts for good, because re-pairing gives the same secret. macOS 14+ app-container protection limits other apps, but not ones with Full Disk Access, and not backups.
- Fix: For signed builds (Developer ID or App Store, which have a stable designated requirement, so no repeated password prompts), store these items in the data-protection Keychain (`kSecUseDataProtectionKeychain: true`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`). Keep the file store only behind a `#if DEBUG` or ad-hoc-build flag. Migrate and then delete the file on first launch of the signed build. Rotating secrets (see Pairing) limits the damage of any past leak.

### [Medium] Re-pairing produces the same secret, so a leaked secret can't be rotated
- Area: Pairing
- Where: macos/Sources/LinkBridgeCore/PairingKeyStore.swift:11-16, 28-35; android/app/src/main/java/com/linkbridge/android/PairingKeyStore.kt:26-41, 53-65
- What: The shared secret is `SHA-256(ECDH(long-term key A, long-term key B))`. Neither the nonces nor the device IDs go into it, and neither side ever regenerates its key. Every pairing between the same two devices yields the same secret.
- Attack: A paired device turns hostile or is stolen, or its secret is copied from the macOS file store (see Secrets). The user removes the device and pairs it again to "reset" it. The old secret still works for TLS-PSK and the upload HMAC, so the attacker can still send files as that device. The checklist item "re-pairing replaces the secret cleanly" does not hold: it replaces the secret with the same value.
- Fix: Derive the secret with HKDF over the ECDH output, salted with both nonces and both device IDs (`info = "linkbridge-psk-v2"`). Or use a fresh ephemeral key pair per pairing. Bump the protocol version so both sides agree.

### [Medium] A LAN attacker can race the user's own pairing and show its request under the user's phone name
- Area: Pairing
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:394-454 (device name taken from the request body); macos/Sources/LinkBridgePresentation/ApprovalQueue.swift
- What: `deviceName`, `deviceId` and `platform` in the Mac's dialog all come from the unauthenticated request. Only one dialog can be open at a time (line 433). The first `/pair/confirm` therefore wins, and the user's real phone gets `pairing_busy`.
- Attack: Someone on the same Wi-Fi watches Bonjour and plaintext pairing traffic. When the user taps Pair on their phone, the attacker sends its own `/pair/request` and `/pair/confirm` with the phone's name and ID. The Mac shows "Pixel 8 wants to pair", which the user expected. The phone shows an error, not a code. A user who doesn't compare codes taps Accept and pairs the attacker, who can then send files to the Mac. This depends on the user skipping the comparison, so it is within the threat model but not a protocol break.
- Fix: Make the code check active on the Mac: ask the user to type or pick the code shown on the phone, rather than only displaying one. Also say in the dialog when the device ID is new versus known, and show the requester's IP address.

### [Medium] A paired device can crash the Mac app with a short encrypted record
- Area: Transport and upload
- Where: macos/Sources/LinkBridgeCore/Security.swift:104-116
- What: `ChunkedDecryptor` accepts any `sealedLength` from 1 up to `chunkSize + 16`. With a length below 16, `tagStart` is negative and `sealedData[..<tagStart]` traps. The record is sliced before any authentication. Kotlin is not affected: a short record fails `doFinal` (`Security.kt:79-86`).
- Attack: A paired device that turns hostile sends a validly signed upload whose first record has length 1–15. The Mac app crashes, and it can do this again each time the app restarts.
- Fix: Require `sealedLength >= 16` (and ideally `> 16`) in the guard at line 105. Add a check that feeds a 1-byte record.

### [Medium] A paired device can queue unlimited file approval prompts on the Mac
- Area: Transport and upload
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:688-712; macos/Sources/LinkBridgePresentation/ApprovalQueue.swift:49-51
- What: Pairing allows one dialog at a time, but file approvals don't: each upload that passes the HMAC check adds an item to `ApprovalQueue` and keeps its connection open for up to 110 s. There is no cap per sender or in total.
- Attack: A paired device that turns hostile, or one that is stolen, opens hundreds of uploads with harmless-looking names. The user sees a stream of prompts and may tap Accept on one just to clear them, or can't find the real one. Each held connection also counts toward the descriptor exhaustion above.
- Fix: Allow one pending approval per sender (refuse more with `429`) and a small total (for example 3). Merge or rate-limit prompts from a sender the user has just declined.

### [Medium] The Mac writes received bytes straight to the final file name before the checksum is checked
- Area: Files on receive
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:674-685 (`accept` creates `Downloads/LinkBridge/<name>`), 631-657 (`finish` checks length and SHA-256 afterwards)
- What: The file appears in `~/Downloads/LinkBridge` under its real name as soon as the user accepts, and grows as data arrives. Mismatches and errors that the code catches do delete it. But if the app crashes, is quit or is killed mid-transfer, or the Mac sleeps or loses power, a truncated file is left behind that looks like a finished one. While it downloads, Finder, Quick Look and Spotlight can already open unverified content. Android does this correctly with `IS_PENDING` (`ReceiveServer.kt:182, 207-217`).
- Attack: A paired device that turns hostile, or just a dropped connection, leaves a partial document the user later opens as if complete. The hostile device can also make the app crash before `finish` runs (see the short-record crash), so the partial file is never cleaned up.
- Fix: Write to a hidden temporary file in the same folder (for example `.linkbridge-<transferId>.part`). Check length and SHA-256, then `rename` to the unique final name. At launch, delete leftover `.part` files.

### [Medium] Pairing dialog text is fully attacker-controlled and can look like a file prompt
- Area: Platform surface
- Where: macos/Sources/LinkBridge/Views/ApprovalContent.swift:17-28 (`Text("Pair with \(name)?")`, no `lineLimit`); macos/Sources/LinkBridge/NotificationController.swift:52-53; source of `name`: ControlServer.swift:448
- What: `deviceName` from an unauthenticated `/pair/request` is shown without limits on length, newlines or character set. The file prompt limits its name to 2 lines (line 35), but the pairing headline doesn't. In the sheet, Return is the default button (Accept), line 46.
- Attack: Someone on the same Wi-Fi sends a pairing request named, for example, `Pixel 8\nwants to send you "Q3 report.pdf" (2 MB)\n`, with padding that pushes the "already paired" warning down. In Notification Center ("…wants to pair") and at a glance, it reads like a routine file from a trusted phone. A user who expects files from that phone presses Return or taps Accept and pairs the attacker. This combines with the race in Pairing.
- Fix: When decoding, limit `deviceName` to ~40 printable characters with no newlines or bidi/control characters (on the server, so every UI benefits). Add `.lineLimit(1)` to the pairing headline. Give pairing and file prompts clearly different layouts and icons. Don't make Accept the default button for pairing.

### [Low] The initiator saves the peer under a device ID from unauthenticated `GET /device`
- Area: Pairing
- Where: macos/Sources/LinkBridgeCore/PairingClient.swift:30, 65-70; android/app/src/main/java/com/linkbridge/android/MainActivity.kt:520-571 (`device` from `fetchDevice`)
- What: The six-digit code covers the two public keys and nonces, but not the device IDs or names. The phone files the new secret under whatever `deviceId` the unauthenticated `/device` reply said.
- Attack: Someone on the same Wi-Fi who sits in the path but lets the key exchange through unchanged rewrites `/device` to carry the ID of another device the phone already trusts. The phone overwrites that trusted peer's entry, so transfers to it fail until it is paired again. This is denial of service only; no key is exposed.
- Fix: Include both device IDs in the code hash (`linkbridge-code-v2`), and save the peer only if the ID from `/device` matches the ID the responder used.

### [Low] Any LAN host can cancel someone else's pairing in progress
- Area: Pairing
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:907-919
- What: `begin` overwrites any pending entry with the same `deviceId`, and `confirm` is one-shot per entry. Neither is tied to the connection or source address that started the pairing.
- Attack: Someone on the same Wi-Fi sees the phone's plaintext `/pair/request` and sends `/pair/request` or `/pair/confirm` with the same `deviceId`. The phone's commitment check then fails, or it gets `no_pending_pairing`. Pairing can be blocked for as long as the attacker keeps doing this. The commit/reveal check prevents a MITM, so this is denial of service only.
- Fix: Bind a pending pairing to its source address, or return a random pairing ID from `/pair/request` that `/pair/confirm` and `/pair/finalize` must send back. Refuse `begin` for a device ID that already has a confirmed entry.

### [Low] The Mac doesn't check that the TLS-PSK identity matches `X-LinkBridge-Device-Id`
- Area: Transport and upload
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:221-248, 523-534 (compare android/.../ReceiveServer.kt:116-120)
- What: Android rejects an upload whose header device ID differs from the identity that completed the TLS handshake. The Mac never reads the negotiated PSK identity. The HMAC still needs the claimed device's secret, so this is not a bypass today.
- Attack: None alone. If the HMAC layer were ever weakened or skipped, a device holding any one PSK could claim to be any other paired device.
- Fix: Read the PSK identity from the connection's `sec_protocol_metadata` (or use a per-identity listener callback) and refuse a mismatch, as Android does.

### [Low] The chunk layer reuses the pairing secret for both AES-GCM and HMAC, and doesn't bind record order
- Area: Transport and upload
- Where: macos/Sources/LinkBridgeCore/Security.swift:13-21, 72-84, 98-126; android/app/src/main/java/com/linkbridge/android/Security.kt:17-22, 64-113
- What: The raw pairing secret is both the AES-GCM key and the HMAC key; only the TLS PSK goes through HKDF. Records have no AAD, sequence number or final-record flag, so records can be reordered, dropped or spliced across transfers without failing GCM. The final SHA-256 check catches this only because the metadata record is under the same key.
- Attack: Only by someone who can already read or write inside the TLS session (that is, who holds the secret). Defence in depth.
- Fix: Derive separate encryption and MAC keys with HKDF. Put `transferId`, the record index and a last-record flag in each record's AAD, and reject a stream that ends without the last record.

### [Low] No size cap or free-space check on receive
- Area: Transport and upload
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:518-521; android/app/src/main/java/com/linkbridge/android/ReceiveServer.kt:100-103, 281
- What: The Mac has no upper bound on `Content-Length`, and Android's limit is `Long.MAX_VALUE - 1024`. Neither checks free space before accepting. A disk-full error is handled: the partial file is deleted (Mac lines 748-756; Android line 222).
- Attack: A paired device that turns hostile sends an approved but huge file that fills the disk. The prompt shows the size, so the user must accept it first.
- Fix: Before asking the user, refuse transfers larger than the free space minus a margin. Optionally add a configurable maximum size.

### [Low] Mac error replies echo local error text to the sender
- Area: Transport and upload
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:766-767
- What: `save_failed` puts `error.localizedDescription` in the JSON reply. This can include local paths such as `/Users/<name>/Downloads/LinkBridge/...`. Only `"` is escaped, so a message with `\` or a control character produces invalid JSON.
- Attack: A paired device learns the Mac's user name and folder layout from a forced write failure. Minor information leak.
- Fix: Return a fixed error code and log the detail locally only.

### [Low] File names can hide their real extension with Unicode tricks, and dot-files are allowed
- Area: Files on receive
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:789-794; android/app/src/main/java/com/linkbridge/android/ReceiveServer.kt:314-319
- What: Sanitizing only replaces `/`, `\` and `:`, then trims whitespace. Bidi controls (U+202E right-to-left override, U+2066–U+2069), other control characters, NUL, and names starting with `.` all pass. A name like `report‮fdp.command` shows as `reportdnammoc.pdf` in the approval prompt and in Finder: it looks like a PDF but is a Terminal script. A `.`-prefixed file is hidden in Finder. Names over 255 bytes fail safely (`write_failed`).
- Attack: A paired device that turns hostile sends a script whose displayed name looks like a document, or a file the user can't see in Finder. This depends on the user opening it. Unconfirmed: whether the App Sandbox's automatic `com.apple.quarantine` reaches these files, so that Gatekeeper warns, has not been checked with `xattr` on a received file.
- Fix: Strip or replace Unicode format and control characters (`\p{Cf}`, `\p{Cc}`), drop leading dots, cap the name at ~200 bytes keeping the extension, and show the extension separately in the prompt. Check that received files carry `com.apple.quarantine`, and set it explicitly if they don't.

### [Low] Old Keychain items and a permissions gap in the macOS file store
- Area: Secret storage
- Where: macos/Sources/LinkBridgeCore/CredentialStore.swift:55, 99-106
- What: Items under the old service `com.linkbridge.credentials` are no longer read but are never deleted, so old secrets stay in the login keychain. Separately, if `credentials.json` already exists with looser permissions (for example, restored from a backup), new secrets are written before `chmod 0600` runs at line 106.
- Attack: A malicious app on the same Mac or a backup reader finds old secrets that the user thinks were replaced. Or, for the moment between the write and the `chmod`, the file can be read under its old permissions.
- Fix: Delete the old Keychain items once, after migrating. Set 0600 before writing (or write to a new 0600 temp file and `rename` it over the old one).

### [Low] File Accept works from a locked Mac's or Android phone's notification, and shows file names on the lock screen
- Area: Platform surface
- Where: macos/Sources/LinkBridge/NotificationController.swift:29-31 (Accept action without `.authenticationRequired`); android/app/src/main/java/com/linkbridge/android/LinkBridgeService.kt:225-243 (no `setAuthenticationRequired(true)`, default lock-screen visibility)
- What: The incoming-file notification's Accept button can be used without unlocking, and its text (sender, file name, size) shows on the lock screen.
- Attack: Someone holding a locked device for a minute accepts a file a hostile paired device is pushing, or reads the names of files being sent. The impact is small: the file lands in Downloads and isn't opened.
- Fix: Mac: add `.authenticationRequired` to the Accept action. Android (minSdk 31): `Notification.Action.Builder.setAuthenticationRequired(true)` on Accept, and `setVisibility(VISIBILITY_PRIVATE)` with a redacted `publicVersion`.

### [Low] Bonjour advertises the user's computer name and a stable device ID on every network
- Area: Platform surface
- Where: macos/Sources/LinkBridgeCore/ControlServer.swift:209-218 with DeviceIdentity.swift:82 (`Host.current().localizedName`); android/app/src/main/java/com/linkbridge/android/DiscoveryService.kt:79-86
- What: The Mac's service name and TXT carry the computer name (often "<First name>'s MacBook Pro") and a UUID that never changes. Android advertises its `deviceId` and model while the service runs.
- Attack: Someone on the same café or office Wi-Fi learns the owner's first name and can recognize the same device across networks and days. The visible `deviceId` is also what the pairing-cancel attack needs.
- Fix: Advertise a random per-network or per-launch instance ID, and send the real `deviceId` only inside the TLS session or pairing flow. Let the user set a display name, with a default that doesn't include their name.

### [Low] Android allows cleartext traffic app-wide
- Area: Platform surface
- Where: android/app/src/main/res/xml/network_security_config.xml:2
- What: `base-config cleartextTrafficPermitted="true"` applies to every host, not just the LAN pairing endpoint. Domain configs can't express "private IP ranges", so this is a known compromise.
- Attack: None today. The app makes no internet requests. A future library or feature that uses `http://` to a public host would silently fall back to plaintext.
- Fix: Keep the global allow, but put a comment and a lint/test in place that fails on any non-RFC1918 `http://` URL. Or move pairing onto the TLS-PSK socket (pairing doesn't need HTTP) and turn cleartext off.

### [Low] A failed key read silently creates a new pairing key
- Area: Platform surface
- Where: macos/Sources/LinkBridgeCore/PairingKeyStore.swift:28-35; macos/Sources/LinkBridgeCore/CredentialStore.swift:10-18, 114-118
- What: (swift-security checklist: OSStatus handling.) `read` returns nil for every failure, including `errSecInteractionNotAllowed` on a locked iPhone and a corrupt `credentials.json` on the Mac. `privateKey` then generates and writes a new key. On the Mac, `write` after a failed `load()` writes a file holding only that key, which deletes every peer secret.
- Attack: Not attacker-driven. A malicious app on the same Mac that can corrupt the file wipes all pairings. Mainly a silent data-loss risk that forces re-pairing, and users learn to accept re-pair prompts.
- Fix: Tell "not found" apart from other errors (OSStatus on iOS, decode errors on the Mac). Generate a key only on not-found, and otherwise surface an error without writing.

## Checked with no finding

**Pairing.** both initiators (Swift `PairingClient.swift:49-52`, Kotlin `ControlClient.kt:58-61`) check the commitment before showing the code. Kotlin compares with `MessageDigest.isEqual`. Swift uses `==`, but commitments are public, so timing doesn't matter. The nonce is accepted once per pairing (`ControlServer.swift:915`), and pairings expire after 110 s (`ControlServer.swift:480`). Re-pairing a known ID sets `replacesExisting` (`ControlServer.swift:452`). The guess rate doesn't matter: the attacker can't choose the code (1 in 10^6 per attempt), and each attempt needs a user dialog, one at a time.

**Transport and upload.** the TLS settings match on all three platforms (TLS 1.2 only, `TLS_ECDHE_PSK_WITH_CHACHA20_POLY1305_SHA256`, HKDF-SHA256 with salt `linkbridge-tls-v1` and info `psk`, lowercased device-ID identity). iOS uses the same Swift code. An unpaired device can't finish the handshake. On the Mac a removed device is also refused per request (`ControlServer.swift:530`), and the listener reloads (`MacModel.swift:233`). On Android the PSK is looked up per connection (`ReceiveServer.kt:77-81`). HMAC comparison is constant-time on both receivers. The timestamp window (±5 min) and replay cache (10 min) line up, so a replay can't outlive the cache. The replay cache only grows for requests with a valid HMAC. Declared versus actual length is enforced on both receivers (Mac 597-600, 640-644; Android 80, 203). Header size is capped at 64 KB on both.

**Files on receive.** path traversal is blocked on both receivers. `/` and `\` are replaced, and a bare `..` or `.` resolves to a folder that exists, so `uniqueDestination` renames it inside `LinkBridge` (`ControlServer.swift:796-814`). Existing files are not overwritten, because `uniqueDestination` runs and the file is created on the main queue in one step. On Android, MediaStore picks a unique name. SHA-256 and the length are checked before the file is reported as received: Mac `ControlServer.swift:640-654`, Android `ReceiveServer.kt:203-219`. Failed transfers delete the partial file on both receivers (except after a crash on the Mac, see above).

**Secret storage.** iOS uses the Keychain with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` and no `kSecAttrSynchronizable`, so items are not synced or restored to another device (`CredentialStore.swift:20-30`). On Android the pairing EC key is a non-exportable AndroidKeyStore key (`PairingKeyStore.kt:53-65`). Peer secrets and the identity token are AES-GCM-encrypted with a Keystore key (`CredentialStore.kt`). `allowBackup="false"`, and `data_extraction_rules.xml` excludes every domain from cloud backup and device transfer. No secrets, codes or nonces go to logs, notifications, `UserDefaults` or `SharedPreferences` in plaintext. Mac pairing notifications deliberately leave out the code (`NotificationController.swift:52-53`).

**Platform surface.** Android exports only the launcher `MainActivity` (no extras are read) and `ShareActivity`. `ShareActivity` accepts only `ACTION_SEND`/`SEND_MULTIPLE` with `content://` URIs from other apps, caps them at 50, sends only after a tap, and never launches a caller intent (`ShareActivity.kt:160-179`). `LinkBridgeService` is not exported and has foreground service type `connectedDevice`. Every `PendingIntent` is explicit and `FLAG_IMMUTABLE` (`LinkBridgeService.kt:208, 226-229, 246-249`). The Accept/Decline request IDs are only reachable through those immutable PendingIntents. Permissions are minimal (no storage permission; MediaStore is used). minSdk 31, targetSdk 36. Mac entitlements are the minimum: sandbox, network client and server, Downloads read-write, user-selected read-only, and app-scope bookmarks, all of which are used (`MacModel.swift:244, 313`). Release builds use the hardened runtime (`scripts/package-mac-app.sh:93`). iOS ATS allows only `NSAllowsLocalNetworking`, Bonjour is limited to `_linkbridge._tcp`, and Keychain accessibility is `WhenUnlockedThisDeviceOnly`. The file prompt shows the sender name from the trusted store, not from the request, and truncates file names in the middle so the extension stays visible.
